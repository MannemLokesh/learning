16. Chain of Responsibility Design Pattern in Java
16.1 Introduction
The Chain of Responsibility Design Pattern is a behavioral pattern that allows you
to pass a request along a chain of handlers. Each handler can either process the request or pass
it to the next handler in the chain.
16.2 Problem it Solves
You want to decouple the sender and receiver of a request, and allow multiple potential
handlers without hardwiring them into your logic.
16.3 What is Chain of Responsibility?
It's a pattern where a group of objects (handlers) are linked in a chain and the request is passed
along until it is handled.
16.4 Real-World Analogy
A customer complaint moves from customer care to supervisor to manager. If one level can't
resolve it, it gets escalated to the next.
16.5 Structure
package com.mannemlokesh;
public abstract class Handler {
protected Handler next;
public void setNext(Handler next) {
this.next = next;
}
public abstract void handleRequest(String request);
}
16.6 Benefits
• Reduces coupling
• Adds flexibility in assigning responsibilities
• Can add/remove handlers dynamically
16.7 Implementation Steps
1. Create an abstract handler with a next reference
2. Implement concrete handlers
3. Chain the handlers
4. Send requests to the first handler

abstract class Logger {
public static int INFO = 1;
public static int DEBUG = 2;
public static int ERROR = 3;
protected int level;
protected Logger nextLogger;
public void setNextLogger(Logger nextLogger) {
this.nextLogger = nextLogger;
}
public void logMessage(int level, String message) {
if (this.level <= level) {
write(message);
}
if (nextLogger != null) {
nextLogger.logMessage(level, message);
}
}
protected abstract void write(String message);
}
class ConsoleLogger extends Logger {
public ConsoleLogger(int level) {
this.level = level;
}
protected void write(String message) {
System.out.println("Console: " + message);
}
}
class FileLogger extends Logger {
public FileLogger(int level) {
this.level = level;
}
protected void write(String message) {
System.out.println("File: " + message);
}
}
class ErrorLogger extends Logger {
public ErrorLogger(int level) {
this.level = level;
}
protected void write(String message) {
System.out.println("Error: " + message);
}
}

Example2: Help Desk Support
package com.mannemlokesh;
abstract class SupportHandler {
protected SupportHandler next;
public void setNext(SupportHandler next) {
this.next = next;
}
public abstract void handle(String issue);
}
class LevelOneSupport extends SupportHandler {
public void handle(String issue) {
if (issue.contains("password")) {
System.out.println("Level 1 solved: " + issue);
} else if (next != null) {
next.handle(issue);
}
}
}
class LevelTwoSupport extends SupportHandler {
public void handle(String issue) {
if (issue.contains("network")) {
System.out.println("Level 2 solved: " + issue);
} else if (next != null) {
next.handle(issue);
}
}
}

class ManagerSupport extends SupportHandler {

public class Example2SupportClient {

Example3: Request Processing Pipeline
package com.mannemlokesh;
abstract class RequestProcessor {
protected RequestProcessor next;
public void setNext(RequestProcessor next) {
this.next = next;
}
public void process(String data) {
String processed = handle(data);
if (next != null)
next.process(processed);
}
protected abstract String handle(String input);
}
class AuthProcessor extends RequestProcessor {
protected String handle(String input) {
System.out.println("Auth Check Passed for: " + input);
return input;
}
}
class LoggingProcessor extends RequestProcessor {
protected String handle(String input) {
System.out.println("Logging Request: " + input);

16.10 Pros and Cons
 Pros
• Loose coupling
• Dynamic chain modification
• Easy to add new handlers
󰣗󰣘 Cons
• No guarantee request will be handled
• Harder to debug due to delegation
16.11 When to Use / Not to Use
Use When:
• You have multiple handlers for a request
• You want decoupled sender/receiver
