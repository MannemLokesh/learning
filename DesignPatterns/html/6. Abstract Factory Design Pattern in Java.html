6. Abstract Factory Design Pattern in Java
6.1 Introduction
The Abstract Factory Pattern is a creational design pattern from the Gang of Four
(GoF). It provides an interface for creating families of related or dependent objects without
specifying their concrete classes.
6.2 Problem it Solves
When your code needs to work with various families of related products (UI elements, services,
etc.), but shouldn't depend on their concrete classes, the Abstract Factory helps isolate that
dependency.
6.3 What is Abstract Factory Pattern?
• It provides an interface to create families of related objects
• Concrete factories implement this interface
• Client code uses the abstract factory without knowing concrete types
6.4 Real-world Analogy
Imagine you're developing software for multiple operating systems. You want to create GUI
elements (buttons, checkboxes, etc.) for each OS without hardcoding each version:
• AbstractFactory: UIFactory
• ConcreteFactory: WindowsUIFactory, MacUIFactory
• Product Interfaces: Button, Checkbox
• Concrete Products: WindowsButton, MacButton, etc.

6.6 Step-by-Step Examples
Example1: Beginner: GUI Toolkit
// Abstract products
package com.mannemlokesh;
interface Button {
void render();
}
interface Checkbox {
void render();
}
// Concrete products for Windows
class WindowsButton implements Button {
public void render() {
System.out.println("Rendering Windows Button");
}
}
class WindowsCheckbox implements Checkbox {
public void render() {
System.out.println("Rendering Windows Checkbox");
}
}
// Concrete products for Mac
class MacButton implements Button {
public void render() {
System.out.println("Rendering Mac Button");
}
}
class MacCheckbox implements Checkbox {
public void render() {
System.out.println("Rendering Mac Checkbox");
}
}
// Abstract factory
interface UIFactory {
Button createButton();
Checkbox createCheckbox();
}
// Concrete factories
class WindowsUIFactory implements UIFactory {
public Button createButton() {
return new WindowsButton();
}
public Checkbox createCheckbox() {

6.7 Pros and Cons
 Pros:
• Groups related products together
• Ensures product consistency
• Makes swapping product families easy
󰣗󰣘 Cons:
• Increases number of classes/interfaces
• Complex when adding new product types
6.8 When to Use / Not to Use
Use When:
• You need to enforce consistency across families
• You expect multiple product variants (themes, OS, environments)
Avoid When:
• Product family is small or fixed
• You don't expect product combinations to change
